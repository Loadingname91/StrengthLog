<objective>
Make every fresh install of FitLog start with a completely empty state — zero routines, zero sessions, zero measurements, zero goals — by deleting the demo-data seed generator and rewiring `buildInitialState()`'s fresh-install branch to return explicit empty values instead. An existing user's saved data must remain provably untouched.

Purpose: New installs currently show five fake routines and ~9 weeks of fabricated workout history, which is confusing on a real device and has to be manually deleted before the app is usable. This plan removes that entirely, closing DATA-01 and DATA-02.
Output: `src/state/StoreContext.jsx` edited in place; `src/lib/seed.js` and `src/lib/rng.js` deleted.
</objective>

## Phase Goal

**As a** FitLog user, **I want to** start every fresh install completely empty and have "Delete all data" require a deliberate press-and-hold, **so that** I never mistake demo data for my real history and can never wipe my data with a single accidental tap.

*(ROADMAP.md's Phase 1 `**Goal:**` line is outcome-shaped prose, not literal "As a/I want to/so that" form — this sentence is a direct reformatting of that Goal plus its 4 Success Criteria and CONTEXT.md D-01–D-08, adding no new scope. This plan (01-01) delivers the first half — the empty-install guarantee; plan 01-02 delivers the second half — the hold-to-confirm gesture.)*

**This plan's slice of the story:** a fresh install shows nothing but a genuinely empty app; an existing user's data is provably untouched.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| localStorage → app initial state | A persisted (or absent, or corrupted) browser/WebView storage blob crosses into `buildInitialState()`'s persisted-vs-fresh decision and, on the fresh branch, into the literal fields returned to `useReducer` as the app's entire starting state tree |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Tampering | `src/state/storage.js` `loadState()` (pre-existing, not modified by this plan) | medium | accept | `loadState()`'s catch-all returns `null` on any `JSON.parse` failure, which is indistinguishable from "no data yet" — a user whose blob became corrupted (quota errors, manual tampering, storage bugs) would be misrouted into the fresh-empty branch, and `saveState()`'s effect would then overwrite the corrupted-but-potentially-recoverable bytes with the empty state on the very next render. This plan does not introduce or worsen this behavior — before this plan, the same misroute silently substituted fake demo data instead, which is arguably a worse outcome (a corrupted-data user would see a normal-looking seeded app and never notice something was wrong). Distinguishing "corrupted" from "genuinely absent" is a distinct hardening improvement outside DATA-01/02's locked scope (CONTEXT.md D-01–D-03) and is not required by any of this phase's 4 success criteria — tracked as a candidate for a future phase rather than pulled into this one. |
| T-01-02 | Tampering | `src/state/StoreContext.jsx` `buildInitialState()` fresh-install branch (Task 1) | high | mitigate | Omitting any field the reducer or selectors expect (e.g. `sequenceIndex`, `routineMode`, `weekdayAssignments`) from the new empty-state literal would leave that field `undefined` on first launch, causing runtime errors or silently corrupted schedule state the first time it's touched (e.g. `ADD_ROUTINE`'s `Object.values(state.weekdayAssignments)`, `FINISH_WORKOUT`'s `state.sequenceIndex` increment) — defeating DATA-01's promise of a clean, immediately-usable empty state. Mitigated by Task 1 specifying the complete 12-key field list (matching the deleted `buildSeed()`'s prior return shape exactly) and Task 2's read-verification pass confirming every key survived the edit. |

</threat_model>
