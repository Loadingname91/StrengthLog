<objective>
Add an opt-in `holdToConfirm` gesture to the shared `ConfirmSheet` component so its confirm button requires an uninterrupted ~1.5s press-and-hold (with a visible left-to-right fill) instead of a single tap, and wire it onto Settings' "Delete all data" call site only. Closes SAFE-01 and SAFE-02.

Purpose: "Delete all data" is currently one accidental tap away from wiping every logged workout, measurement, and goal with no undo. This plan makes that impossible without a deliberate, sustained gesture.
Output: `src/components/ConfirmSheet.jsx` extended with the hold gesture; `src/screens/Settings.jsx`'s delete-all call site opts in.
</objective>

## Phase Goal

**As a** FitLog user, **I want to** start every fresh install completely empty and have "Delete all data" require a deliberate press-and-hold, **so that** I never mistake demo data for my real history and can never wipe my data with a single accidental tap.

Plan 01-01 delivers the first half — the empty-install guarantee; this plan (01-02) delivers the second half — the hold-to-confirm gesture.)*

**This plan's slice of the story:** the app's single most destructive action can no longer fire from a fat-finger tap.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-03 | Tampering | `src/components/ConfirmSheet.jsx` confirm button + `src/screens/Settings.jsx` "Delete all data" | high | mitigate | Pre-phase behavior: a single accidental tap (fat-finger, misclick, or a bump while scrolling) fires `DELETE_ALL_DATA` immediately with no recovery — this is the exact vulnerability SAFE-01/SAFE-02 exist to close. Mitigated by Task 1's uninterrupted 1500ms pointer-hold requirement, with no `onClick` handler present on the hold-variant button so a fast tap or a synthetic click cannot bypass the hold. |
| T-01-04 | Tampering | `src/components/ConfirmSheet.jsx` hold-timeout lifecycle (Task 1) | high | mitigate | A `setTimeout` scheduled by `onPointerDown` is not automatically tied to the button's mount lifecycle — if the sheet unmounts or `open` flips to `false` between pointer-down and the 1500ms mark without a pointer-up/leave/cancel event firing first (e.g. a rapid route change or the OS reclaiming the WebView), the timeout could still fire later and dispatch `DELETE_ALL_DATA` against a screen the user is no longer viewing, defeating D-07's "release cancels cleanly" guarantee in spirit even though no explicit release occurred. Mitigated by Task 1's cleanup `useEffect` that clears the pending timeout on unmount, in addition to the existing pointer-up/leave/cancel handlers. |
| T-01-05 | Denial of Service (minor) | `src/components/ConfirmSheet.jsx` hold-variant button (Task 1) | low | mitigate | Android WebView's native long-press behavior (text-selection callout / context menu) could interrupt or visually collide with the custom hold gesture mid-press, since a press-and-hold is exactly what triggers that native UI. Mitigated by `touchAction: 'none'`, `WebkitUserSelect: 'none'`, `userSelect: 'none'`, and `onContextMenu={(e) => e.preventDefault()}` on the hold-variant button, per UI-SPEC's "Trigger wiring" section. |
