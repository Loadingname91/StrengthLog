# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Phase Scope Note

This phase's UI surface is narrow and almost entirely pre-decided in `01-CONTEXT.md` (D-01 through D-08). No new screens, no new color tokens, no new copy. The only open design surface is the **hold-to-fill animation contract** on the existing `ConfirmSheet` danger button, which this document specifies precisely so `gsd-executor` can implement it without ambiguity and `gsd-ui-checker` has concrete criteria to validate against.

DATA-01/DATA-02 (empty state on fresh install) require **no new UI** — `Home.jsx`, `Routines.jsx`, and `StatsHub.jsx` already render correctly for zero-data states via existing conditionals (`hasHistory`, `ordered.filter(Boolean)`, `"No workouts logged yet."` in `StatsHub.jsx:236`, `"No goals yet — add one from Home."` in `Settings.jsx:70`). This is a functional/data-layer change (removing `seed.js`), not a visual one. Verify these existing empty-state renders still look correct once seed data is removed, but do not design new empty-state copy or layout for them in this phase.

Existing app convention (not redesigned this phase) — Tailwind v4 utility spacing, predominantly multiples of 4:

| Token | Value | Usage (existing) |
|-------|-------|-------|
| xs | 4px | icon gaps |
| sm | 8px | `gap-2`, compact spacing |
| md | 12–16px | `py-3`/`gap-3` (button vertical padding), `p-5` (sheet padding) |
| lg | 20–24px | `p-5` sheet edge padding, `pb-5` |
| xl | 32px+ | not used at this component scale |

**Exceptions:** `p-3.5` (14px) is already used for list-row/button padding in `Settings.jsx` (`NavRow`, "Delete all data" row). Pre-existing convention, not introduced or changed by this phase.

**This phase's specific spacing constraint:** The hold-to-fill overlay adds **zero additional padding/margin** to the `ConfirmSheet` confirm button. The button's existing box model (`flex-1 rounded-2xl py-3 text-sm font-semibold`) is unchanged — the fill is a purely internal, absolutely-positioned visual layer, not a layout change. Touch target stays at its current ~44px effective height (`py-3` + `text-sm` line height); do not shrink the button to accommodate the fill treatment.

## Color

Existing token palette (`src/index.css`), reused as-is — no new CSS custom properties introduced:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `var(--bg)` / `var(--surface)` | App background / sheet surface |
| Secondary (30%) | `var(--surface-alt)`, `var(--border)` | Cards, dividers, secondary chrome |
| Accent (10%) | `var(--accent)` | Reserved for: primary avatar badge, active/selected controls, non-destructive `ConfirmSheet` confirm buttons (`danger=false` call sites) — **not used anywhere in this phase's delete-confirmation flow** |
| Destructive | `var(--danger)` | "Delete all data" row text (Settings), `ConfirmSheet` confirm button background when `danger` (unchanged from today) |

**Accent reserved for:** avatar initial badge (Home), segmented-control active state, non-destructive confirm actions. The hold-to-fill delete button intentionally uses **no accent color** — it is a destructive-only interaction and must stay visually distinct from accent-colored (safe/positive) actions.

**Fill overlay color (new, phase-specific):** `rgba(255, 255, 255, 0.25)` — a fixed white wash, not a new theme token. Applied identically in light and dark theme since it sits as a semi-transparent layer on top of `var(--danger)`, which already has distinct light/dark values (`#B3412A` light / `#E0705A` dark) — the white overlay reads as a visible "fill" against both without needing per-theme tuning.

## Interaction & Animation Contract (phase-specific — feeds Checker Dimension 2: Visuals)

This is the load-bearing section of this UI-SPEC. It encodes D-04 through D-08 from `01-CONTEXT.md` into exact, implementable values.

### Mechanism: linear width-fill overlay (locked choice, resolving Claude's Discretion)

Reuses the exact pattern already established by `src/components/ProgressBar.jsx` (`overflow-hidden` container + inner div with `width: {pct}%` animated via CSS `transition-[width]`) rather than introducing a radial/conic-gradient wipe or a `requestAnimationFrame` loop. Rationale: this is the only progress-fill pattern that already exists in the codebase; reusing it keeps the interaction visually and technically consistent with `ProgressBar` and needs no new CSS techniques.

**DOM structure for the confirm button (when `holdToConfirm` is true):**
- Outer `<button>` keeps its existing classes/style (`flex-1 rounded-2xl py-3 text-sm font-semibold text-white`, `background: var(--danger)`) plus `relative overflow-hidden` added for the overlay to clip correctly against the `rounded-2xl` corners.
- Inner absolutely-positioned fill layer: `absolute inset-y-0 left-0`, `background: rgba(255,255,255,0.25)`, `width` driven by hold progress state, `pointer-events-none`.
- Label text wrapped in a `relative z-10` span so it stays fully legible above the fill at all times (no opacity/color change to the text itself, ever).

### States

| State | Trigger | Fill width | Transition | Button base color |
|-------|---------|-----------|------------|-------------------|
| Idle | sheet opens / no pointer down | 0% | none | `var(--danger)` (unchanged from today) |
| Holding | `onPointerDown` on the confirm button | animates 0% → 100% | `width 1500ms linear` | `var(--danger)` (unchanged) |
| Cancelling | `onPointerUp` / `onPointerLeave` / `onPointerCancel` before 1500ms elapses | animates current% → 0% | `width 150ms ease-out` | `var(--danger)` (unchanged) |
| Completed | 1500ms elapses while still holding | reaches 100% | (fill completes, then `DELETE_ALL_DATA` dispatches and the sheet unmounts immediately — no lingering "full" frame to design for) | n/a — component unmounts |

**Exact timing values (locked):**
- Hold duration: **1500ms**, matching D-04.
- Fill easing during hold: **linear** — the fill rate must track elapsed hold time 1:1 so the fill reads as an accurate progress indicator, not a decorative animation.
- Cancel-reset easing: **150ms ease-out** — deliberately much faster and eased (vs. the slow linear hold-fill) so a release reads immediately and distinctly as "cancelled," never as "the hold continuing in reverse."

**No other visual change accompanies the hold** — no scale/press transform, no shadow change, no haptic feedback (do not add `@capacitor/haptics`; not an existing dependency and out of scope this phase), no button-color change, no new copy overlay ("Hold to delete" text, a countdown number, etc.). D-05's "no new UI chrome" constraint means the fill overlay is the *only* new visual element.

### Trigger wiring (resolving the pointer/touch discretion note)

- Use unified Pointer Events (`onPointerDown`, `onPointerUp`, `onPointerLeave`, `onPointerCancel`) rather than separate touch/mouse handlers — works correctly on both Android WebView (touch) and browser dev testing (mouse) without duplicated logic.
- `onPointerDown` starts a `setTimeout(1500)` that dispatches `DELETE_ALL_DATA` and closes the sheet when it fires; simultaneously sets the holding state that drives the CSS width transition described above.
- `onPointerUp`, `onPointerLeave`, and `onPointerCancel` all clear the pending timeout and revert to the Cancelling state — per D-07, this must be silent: no toast, no partial state, no console output.
- The button's native `onClick` must NOT independently fire `onConfirm` when `holdToConfirm` is true — a fast tap (pointerdown+pointerup pair firing a synthetic click) must not bypass the hold. Only the 1500ms timeout may call `onConfirm`.
- Apply `style={{ touchAction: 'none', WebkitUserSelect: 'none', userSelect: 'none' }}` to the button while `holdToConfirm` is active, and suppress the context menu (`onContextMenu={(e) => e.preventDefault()}`). This prevents Android WebView's native long-press behavior (text-selection callout / context menu) from interrupting the custom hold gesture — a real risk on a press-and-hold interaction that the codebase has not previously needed to guard against (existing long-press patterns in the app are a *different* mechanic — contextual menu triggers on goals/completed sets — not a fill-confirm gesture; do not reuse or conflate).

### Reusability constraint (D-08, encoded as a hard visual constraint)

`ConfirmSheet`'s two other call sites — `src/screens/Routines.jsx` (delete routine) and `src/screens/ActiveWorkout.jsx` — must render **pixel-identical** to their current tap-to-confirm appearance. The new `holdToConfirm` prop must default to `false`/undefined, meaning: no `relative overflow-hidden` wrapper, no fill layer, no pointer-event wiring, plain `onClick={onConfirm}` exactly as today. Only `Settings.jsx`'s "Delete all data" call site passes `holdToConfirm`.
