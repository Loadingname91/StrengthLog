<objective>
Make logging a set on a phone take fewer taps: bigger weight/reps inputs, confirm-to-advance focus chaining between fields, and automatic set completion once both values are valid — while leaving the manual checkmark as a working override.

Purpose: this is v1.1's independent, lowest-risk phase — no data model change, no interaction with Phase 6's `sequence` work. It directly serves the project's stated core value (fast, reliable mid-session logging).
Output: `ActiveWorkout.jsx`'s `SetRow` gains larger inputs, ref-based focus chaining lifted to its parent, and one new auto-dispatch call site for `TOGGLE_SET_DONE`. No reducer action shapes change.
</objective>

## Phase Goal

**As a** person logging a set mid-workout, **I want to** type a weight and reps and have the app move on for me, **so that** logging never interrupts my set with fiddly re-tapping between tiny fields.

**This plan's slice of the story:** the entire phase — there is no second plan.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Auto-dispatch → data integrity | Auto-mark-done dispatches the exact same `TOGGLE_SET_DONE` action the manual checkmark already uses — no new reducer code path, so no new correctness risk beyond "does it fire at the right time." |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|--------------|------------------|
| T-05-01 | Tampering (false confidence) | Auto-mark-done trigger | medium | mitigate | Firing on every `onChange` keystroke (rather than confirm-only) would risk marking a set done mid-type (e.g. typing "1" of "10"), then immediately "undone" by a subsequent keystroke if a naive effect re-ran — a flickery, confusing UX bug, not a security issue, but a correctness one. Mitigated by triggering only from the same explicit confirm action (Enter/blur) used for focus-advance, never from `onChange`, and by never auto-un-marking (D-07: one-directional). |

</threat_model>
