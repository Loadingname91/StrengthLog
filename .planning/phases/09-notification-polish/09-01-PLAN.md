<objective>
Everything in Phase 9 that's purely native: the rest-done alert stops relying on channel-default sound/vibration (which doesn't duck concurrent music) and instead plays through the app's own audio-focus-aware MediaPlayer/Vibrator calls (NOTIF-16); the notification's "Finish" action stops being a plain "open the app" tap and becomes a service-routed action that both launches the app and durably records that Finish was tapped, reusing Phase 8's existing pending-action machinery (the native half of NOTIF-15); and the pending-action queue gets a size bound (hardening NOTIF-14's durability guarantee).

Output: changes to `WorkoutService.kt` and `PendingActionStore.kt` only. No plugin change, no JS change — 09-02 consumes what this plan produces.
</objective>

## Phase Goal

**As a** person finishing a set with music playing, **I want to** hear the rest-done ding clearly without it fighting my music or getting drowned out, **so that** the alert actually works in the one condition (music playing) it's most likely to be needed in.

**This plan's slice of the story:** the native audio/haptic mechanism, plus the native trigger point for the notification's "Finish" action. 09-02 wires the JS consumption side.

## Refinements over 09-CONTEXT.md, found while working out the exact code

- **`postRestDoneAlert()`'s builder-level `.setVibrate()`/`.setSound()` fallback lines (Phase 8) are removed, not kept alongside the new ducked audio.** `NotificationCompat.Builder.setSilent(true)` suppresses a notification's sound/vibration uniformly across API levels (it's implemented in the compat library itself, not OS-version-gated) — keeping the old builder-level calls would be dead code once `setSilent(true)` is set, and *not* setting `setSilent` would risk the channel's own default sound playing **in addition to** the new ducked `MediaPlayer` ding, which is the double-audio bug this phase exists to avoid, not introduce.
- **NOTIF-15's native half is scoped to exactly one thing: what the "Finish" `PendingIntent` targets.** 08-CONTEXT.md's original D-02 sketch mentioned `MainActivity.handleOnNewIntent` and a fresh JS-native surface for it; working through what already exists (Phase 8's `PendingActionStore`/`enqueueAndEmit`/effect E drain, all built for exactly "an action tapped on the notification needs to reach the reducer reliably") makes a *second* delivery mechanism redundant. `ACTION_FINISH_TAPPED` reuses `enqueueAndEmit("FINISH_TAPPED", 0)` verbatim — the only native code this plan adds beyond the ding is the PendingIntent retargeting and one `startActivity()` call (a service *can* start an activity directly when the intent carries `FLAG_ACTIVITY_NEW_TASK`, which `appLaunchIntent()` already sets for the ongoing notification's content intent).
- **API 24/25 fallback paths are kept deliberately small.** `AudioFocusRequest` (the builder class) and `VibratorManager` are both API 26+/31+; minSdk is 24, so a hard `Build.VERSION.SDK_INT` branch is unavoidable here (unlike most of this project's Android code, which sticks to AndroidX compat classes specifically to avoid this) — there is no AndroidX compat shim for audio focus below API 26. Each branch is one line of legacy API call, not a parallel implementation.
</design_refinement>
