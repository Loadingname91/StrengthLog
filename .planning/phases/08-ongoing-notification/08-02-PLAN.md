## Refinements over 08-CONTEXT.md, found while working out the exact JS wiring

- **`restUntil` crosses the JS↔native bridge as epoch milliseconds, not the ISO string the reducer stores it as.** `activeWorkout.restUntil` is an ISO string internally (unchanged — nothing about the reducer's shape changes). Converting to `new Date(...).getTime()` happens entirely inside `nativeNotifications.js`, right before the plugin call. This avoids any date-parsing on the Kotlin side (no `java.time`, which would need Java 8+ API desugoring this project doesn't have configured, and no brittle `SimpleDateFormat` pattern-matching) — the boundary is a plain number both sides handle natively.
- **`startWorkout()` becomes async and returns a boolean** (`true` = "show the fallback banner"), replacing the separate `native.requestNotificationPermission()` call `useWorkoutNotifications.js` effect A currently makes right after `native.startWorkout(...)`. `startWorkout()` now does the permission request itself (it already has to know the result to decide whether to start the service), so the second call becomes redundant rather than additive. This is the one behavioral seam where NOTIF-13 actually gets decided.
- **A `notifyOngoing: false` return is `false` (no banner), not `true`.** Settings' own copy already tells the user "Rest-timer alerts run inside this notification, so turning it off also turns those off" — that's a deliberate, already-explained choice, not the permission-denied failure state NOTIF-13 describes. Conflating the two would nag the user about a setting they just chose themselves.
- **A `serviceActive` module-level flag in `nativeNotifications.js` guards `updateWorkout()`/`stopWorkout()`.** Capacitor's `Context.startService()` (used for `update`/`stop`/Skip/+15s — anything after the initial `start()`) will *start* a stopped service if it isn't already running. Without this guard, calling `update()` while the service was never started (permission denied, or `notifyOngoing` off) would silently bring the foreground service up anyway — exactly what NOTIF-13 exists to prevent. `startWorkout()` sets it `true` only after a real `WorkoutNotification.start()` call succeeds; `stopWorkout()` resets it and skips the native `stop()` call entirely when it's already `false`.
- **Effect A gains two payload fields (`startedAt`, `notifyOngoing`) and a `dispatch` call; it is not otherwise restructured.** `startedAt` (already on `activeWorkout`, used today for finish-duration math) becomes the chronometer's up-counting base — without it, a workout resumed after a cold app restart would show the chronometer counting from zero instead of true elapsed time. `useWorkoutNotifications` itself gains a `dispatch` parameter (its call site in `StoreContext.jsx` changes from `useWorkoutNotifications(state, exercises)` to `useWorkoutNotifications(state, dispatch, exercises)`), needed both for the fallback-banner dispatch and for effect E's action drain below.
</design_refinement>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| `WorkoutService` (08-01) → `PendingActionStore` → `useWorkoutNotifications.js` effect E → reducer | The full round-trip a malformed or stale entry could ride to reach `dispatch()`. This plan owns the JS-side half of the guard 08-01 flagged (T-08-04). |
| JS → `WorkoutNotificationPlugin` → `WorkoutService` (service liveness) | `serviceActive`'s absence would let `updateWorkout()`/`stopWorkout()` silently (re)start a service the user or the OS explicitly kept from starting — the exact failure NOTIF-13 exists to prevent. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|--------------|------------------|
| T-08-06 | Tampering (stale/cross-workout action) | effect E's `apply()` | high | mitigate | Closes 08-01's T-08-04: every drained or live-emitted action is checked against `stateRef.current.activeWorkout?.id` before dispatch; a mismatch (the app finished that workout and started a new one before the action was drained) is silently dropped. Covered by Task 5's mismatched-`workoutId` test. |
| T-08-07 | Elevation of Privilege (silent service start) | `updateWorkout`/`stopWorkout` without `serviceActive` guard | high | mitigate | Both functions no-op when `serviceActive` is `false` (permission denied or `notifyOngoing` off), so `Context.startService()`'s "start if not running" behavior can never bring the foreground service up as a side effect of an unrelated content update. This is the concrete mechanism behind NOTIF-13's guarantee. |
| T-08-08 | Repudiation (duplicate action application) | `ack()` timing vs. the fast-path listener | medium | mitigate | Each drained action is acked (`WorkoutNotification.ack`) immediately after `apply()` in the same loop iteration, and the live-listener path acks immediately after applying too — the only window for a double-apply is the two paths racing on the exact same action, which `PendingActionStore.ack` (08-01, keyed by a UUID `id`) makes idempotent: acking an already-removed id is a no-op. |
| T-08-09 | Information Disclosure | Fallback banner copy | low | accept | States only that notifications are blocked and where to fix it — no data exposure beyond what Settings' existing permission row already shows. |

</threat_model>
