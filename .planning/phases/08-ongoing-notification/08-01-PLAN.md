<design_refinement>
## Refinements over 08-CONTEXT.md, found while working out the exact service code

- **`fitlog_rest_v1` is never recreated natively.** D-06 says this channel "already exists from Phase 7 and gets reused here." Rather than also re-declaring it via `NotificationChannelCompat` natively (uncertain API surface for lockscreen-visibility on this androidx.core version, and redundant), `NotificationChannels.kt` only creates the genuinely new `fitlog_workout_v1` channel. The rest channel is guaranteed to exist by the time a workout can start because `ensureChannels()` (Phase 7, `src/lib/nativeNotifications.js`) already runs once on every native app launch, before any "Start Workout" tap is possible.
- **Every `onStartCommand` call re-runs `ServiceCompat.startForeground` first, unconditionally (except `ACTION_STOP`, handled separately below).** Rather than trying to distinguish "cold start" from "already running" calls (which would need to reason about the 5-second rule differently per action), the service always posts the notification as its first statement, every single call. This is safe/idempotent when already foregrounded and trivially satisfies D-03 for the one call where it actually matters (the very first `ACTION_START`). `ACTION_SKIP_REST`/`ACTION_ADD_15S` mutate state and then re-post via a lightweight `postOngoingNotification()` (a plain `NotificationManagerCompat.notify()`, not a second `startForeground` call) so the notification reflects the *post*-mutation state, not the momentarily-stale state from the mandatory first post.
- **`ACTION_STOP` is checked before anything else in `onStartCommand` and returns early**, skipping the "always post first" step entirely — there is no 5-second obligation to satisfy on a stop, and posting-then-immediately-removing the notification would only risk a visible flash.
- **`START_NOT_STICKY` throughout.** If Android kills the process and later respawns the service with a null `Intent` (the `START_STICKY` contract), there is no in-memory workout state left to build a real notification from. Since `useWorkoutNotifications.js`'s existing effect A already re-sends a fresh `ACTION_START` the moment the JS layer reinitializes after a cold restart (it starts the workout notification on mount whenever `activeWorkout` is already non-null — Phase 7 behavior, unchanged), there is nothing useful for a sticky respawn to do. Full state survival across a killed *process* (as opposed to a killed *service* while the app is merely backgrounded) is Phase 9's `NOTIF-14`, not this phase.
- **The service never references the plugin class.** 08-CONTEXT.md's D-07 sketch has the service reaching into `WorkoutNotificationPlugin` directly to emit the fast-path event — but the plugin (08-02) doesn't exist yet when this plan compiles, and depending forward on a later plan's file would break this plan's own "independently adb-testable" must_have. Instead `WorkoutService` exposes a settable `actionListener` callback on its companion object; 08-02's plugin plugs into it from its `load()`. The dependency points from the newer file to the older one, never backward.
- **Wake lock acquired with a hard cap (`delayMs + 5_000`), not indefinitely.** `PowerManager.WakeLock.acquire(long)` with a timeout is a safety net in case a future bug ever leaves `cancelRestAlarm()` uncalled — the lock self-releases instead of draining battery forever. The design (D-01) already time-bounds rest to 60-180s logically; this just makes that bound enforced at the OS level too, not only in application logic.
</design_refinement>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Android system → `WorkoutService` (notification action taps) | `Skip rest`/`+15s` `PendingIntent`s can be triggered while the app is fully backgrounded or the phone is locked — the service must treat these as fully untrusted external triggers even though they originate from its own notification. |
| `WorkoutService` → `PendingActionStore` (SharedPreferences) | The only persistence this phase adds outside the existing reducer/localStorage; a corrupt or stale entry must never crash the service or (once 08-02 drains it) get misapplied to a workout other than the one it was recorded for. |
| `WorkoutService` → wake lock / OS power management | Holding a `PARTIAL_WAKE_LOCK` incorrectly (never released, or released too early) is this plan's most consequential native bug — either a battery-drain complaint or a silently-missed rest alert. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|--------------|------------------|
| T-08-01 | Spoofing | `WorkoutService`'s Intent-based actions | medium | mitigate | `android:exported="false"` (Task 1's manifest block) — only this app's own `PendingIntent`s (created by this same service) can invoke it; no other app on the device can send it an `ACTION_SKIP_REST`/`ACTION_STOP` intent. |
| T-08-02 | Denial of Service | Wake lock lifecycle | high | mitigate | Every code path that arms the lock (`armRestAlarm`) routes through `cancelRestAlarm()` first, and every exit path (`fireRestDone`, `teardown`, `onDestroy`) calls it too — plus the `acquire(delayMs + 5_000)` hard timeout from design_refinement as a second, OS-enforced backstop if application logic ever fails to release it. |
| T-08-03 | Denial of Service | `ForegroundServiceDidNotStartInTimeException` (D-03) | high | mitigate | `onStartCommand`'s non-STOP branch does nothing but read Intent extras (in-memory, no I/O) before calling `ServiceCompat.startForeground` — no SharedPreferences access, no notification-content computation that could block, occurs before that call. |
| T-08-04 | Tampering | Stale `PendingActionStore` entries applied to the wrong workout | medium | accept-with-mitigation-elsewhere | This plan only writes entries (tagged with the `workoutId` active at enqueue time); the workoutId-match guard that *prevents* misapplication lives in 08-02's JS drain logic, per 08-CONTEXT.md's explicit decision ("Drop any action whose workoutId doesn't match the current workout"). Flagged here for traceability; 08-02's plan must include it as a must_have. |
| T-08-05 | Information Disclosure | Notification content on the lock screen | low | accept | Exercise names only, no weights/reps/health data, on a single-user personal device — same exposure Phase 7 already shipped for PR/reminder notifications. |
