  <action>
    For every `onClick`, `onChange`, `onPointerDown`/`Move`/`Up`/`Cancel`, and drag handler in the files above, trace it to what it actually does (dispatch payload shape, navigate target, local state update) and compare against what the control visually claims to do (its label, icon, or position in a destructive-action flow). Flag anything where the two disagree, where a destructive action has no confirmation, where an overlay/menu has no way to dismiss without picking an option, or where a shared piece of state can end up duplicated/inconsistent across sibling instances.

    Fix every defect found, matching this codebase's existing conventions exactly rather than inventing new UI patterns:
    - **Routines.jsx**: the per-routine "⋮" actions menu (`menuFor` state) had no backdrop, so tapping anywhere outside it left it open indefinitely. Added a `fixed inset-0 z-[5]` backdrop (`onClick={() => setMenuFor(null)}`) rendered as a sibling before the menu popup, matching the existing `ConfirmSheet`/`AddGoalSheet`/`ScheduleEditSheet` full-screen-backdrop pattern already used elsewhere in this app.
    - **RoutineBuilder.jsx**: `BlockRow`'s "⋮" menu used `useState` local to each row instance, so tapping block A's menu then block B's menu without closing A's first left both open simultaneously — the menu button's implicit "show only this block's actions" contract was broken. Lifted the open/closed state to the parent (`blockMenuFor`, mirroring `Routines.jsx`'s `menuFor`) so only one block menu can be open at a time, passed down as `menuOpen`/`onToggleMenu`/`onCloseMenu` props, and added the same outside-tap backdrop.
    - **Home.jsx / WorkoutOverview.jsx / reducer.js**: "Start Workout" on both screens unconditionally dispatched `START_WORKOUT`, which the reducer implements as an unconditional overwrite of `state.activeWorkout` — silently destroying any in-progress session (logged sets, elapsed time) with zero warning. This directly contradicts the project's core value and was newly easy to trigger now that Phase 2's `SessionBar` lets a user navigate to other routines mid-workout. Fixed both call sites to resume the existing session instead (`if (state.activeWorkout) { navigate('/workout'); return }`), mirroring `BottomNav.jsx`'s `handleLog`, which already did this correctly. Added a reducer-level no-op guard (`if (state.activeWorkout) return state` at the top of the `START_WORKOUT` case) as a defense-in-depth backstop for any future call site that forgets the UI-level check, matching this codebase's existing convention of defensive reducer guards (e.g. `if (!state.activeWorkout) return state` elsewhere in the same reducer).
    - **Measurements.jsx**: the per-entry trash-icon button dispatched `DELETE_MEASUREMENT` directly on a single tap with no confirmation — inconsistent with every other delete in the app. Added a `deleteTarget` state and a `ConfirmSheet` (single-tap confirm, not hold-to-confirm — that gesture is reserved for the app-wide "Delete all data" wipe per SAFE-01/02), matching `Routines.jsx`'s delete-routine flow exactly.
    - **Settings.jsx**: the per-goal trash-icon button had the identical unprotected-delete defect. Fixed the same way with a second `ConfirmSheet` instance (`deleteGoalTarget`).

    Everything else audited (Home's goal cards, StatsHub's tab switching and all three tab bodies, ActiveWorkout's rest timer/set toggling/RIR chips/exercise-chip navigation, CsvImport's multi-step wizard, ExportInsights' CSV/PDF export and date-range filtering, ExerciseDetail's metric toggle and notes autosave, WorkoutSummary's note-and-done flow, ExerciseLibrary's search/filter/create-custom flow, and every shared component's own interaction — SegmentedControl, WeekStrip's week pagination and day-tap navigation, BodyHeatmap's region-tap filtering) was traced and confirmed to do exactly what it claims, with no changes needed.

    One finding was deliberately NOT fixed — RoutineBuilder's drag-to-reorder gesture lacks a `visibilitychange`/`blur` interrupt safeguard (the same category as Phase 1's CR-01, but lower severity since reordering is non-destructive and reversible, and `onPointerCancel` already covers the overwhelming majority of real interruption cases). Recorded in `PROJECT.md`'s Context section with the explicit reasoning per QA-02's requirement, rather than silently skipped.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| User tap → destructive dispatch | Every delete action (routine, measurement, goal, all-data) now goes through a `ConfirmSheet` before the corresponding `DISPATCH` fires — no destructive action in the app is reachable from a single, unconfirmed tap |
| Active session → re-start attempt | `START_WORKOUT` can no longer silently replace an in-progress `activeWorkout`, at both the UI call-site level and the reducer level |
